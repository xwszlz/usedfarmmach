## 2. CSP 白名单：每一条都要能指出代码出处

CSP 最怕"宁滥勿缺"式堆砌——加太多等于没加，加漏了就是白屏。下面每一条都对应实测来源。

| 指令 | 值 | 为什么必须有 |
|---|---|---|
| `default-src` | `'self'` | 兜底。未列出的类型一律只允许同源。 |
| `script-src` | `'self' 'unsafe-inline'` | **必须有 `'unsafe-inline'`**：实测 `.com` 首页有 **22 个内联 `<script>`**，其中 **17 个是 RSC payload** 的 `self.__next_f.push(...)`。去掉这一项整站白屏。 |
| | `https://mc.yandex.ru` | Yandex Metrica（`src/app/[locale]/layout.tsx:74`）。⚠️ 它是 `document.createElement('script')` **动态注入**的，SSR HTML 里看不到 `<script src="mc.yandex.ru">`，用 `curl` 抓页面会漏掉——这是"只看 curl 就配 CSP"最典型的踩坑点。 |
| | `https://cdn.paddle.com` | Paddle.js 结账（`src/app/[locale]/credits/recharge-form.tsx:46`）。`.cn` 因 `if (!isCom) return` 永不加载，但 CSP 是两站共用一份配置，`.com` 充值页要靠它，必须写。 |
| `style-src` | `'self' 'unsafe-inline'` | 项目用 **MUI（emotion）**，运行时动态插入 `<style>` 标签。 |
| `img-src` | `'self' data: blob:` + `https://*.aliyuncs.com` | 实测 `.cn` 首页 **100 处**图片来自 `usedfarmmach-oss.oss-cn-beijing.aliyuncs.com`。 |
| | `https://mc.yandex.ru` | Metrica 的 `watch/109732268` 埋点像素（`<noscript>` 里那个 1×1 图）。 |
| `frame-src` | `'self' https://*.paddle.com` | Paddle 结账浮层是 iframe。 |
| `connect-src` | `'self'` + Yandex + Paddle + aliyuncs | 前端 XHR 基本都是同源 `/api/*`；Yandex 上报、Paddle 轮询、OSS 直传需要出网。 |
| `font-src` | `'self' data:` | `next/font` 自托管字体，同源。 |
| `frame-ancestors` | `'self'` | 防点击劫持。**Report-Only 下此指令不生效**，所以 `X-Frame-Options` 必须真上（见 §3.1）。 |
| `object-src` | `'none'` | 本站不用 Flash/Java 插件，直接封死。 |
| `base-uri` / `form-action` | `'self'` | 防注入 `<base>` 劫持相对路径、防表单被改投第三方。 |

### 2.1 一个必须排除的误伤风险

小程序 `shendiao-miniprogram/pages/about/about.js:28` 用 `<web-view src="https://usedfarmmach.cn">` 嵌我们的站点。

**结论：不受影响。** 微信小程序的 `<web-view>` 是**原生 WebView 控件做顶层导航**，不是 iframe，`X-Frame-Options` 与 `frame-ancestors` 对顶层导航完全不适用。已确认不会白屏。

（如果哪天真出现白屏，排查方向是兜底域名白名单，不是这两个头。）

## 3. 代码改动

### 3.1 `next.config.js`

**为什么写在这里而不是 `vercel.json`**：`vercel.json` 只对 Vercel 平台生效，`.cn` 走阿里云 ECS + Docker standalone **完全读不到**。`next.config.js` 的 `headers()` 是应用层能力，两站同一个构建配置、两边同时生效，不会漂移。

改动内容：
1. 新增 `CSP_DIRECTIVES` 数组 + `CSP` 常量（`join("; ")`）——用数组而不是一长行字符串，是为了让 diff 可读、每条指令能单独定位。
2. `headers()` 新增一条 `source: "/(.*)"` 的全局规则，下发 5 个头：`Content-Security-Policy-Report-Only`、`X-Frame-Options`、`X-Content-Type-Options`、`Referrer-Policy`、`Permissions-Policy`。
3. `poweredByHeader: false`。

**三个设计取舍：**

- **不写 `Strict-Transport-Security`**。Vercel 与 `.cn` nginx 已各自下发 HSTS，应用层再写一份会出现两个同名头，浏览器只认第一个，反而让两站的有效期变得不可预测。
- **`'unsafe-eval'` 只在 dev 放行**（`IS_DEV` 判断）。`next dev` 的 HMR / React Refresh 依赖 eval；生产构建不需要，已实测生产头里不含 `'unsafe-eval'`。
- **全局规则与 subsidy 的 `no-store` 共存**。Next 会把所有命中的规则**追加合并**，不会互相覆盖——已实测验证（见 §4.2）。

### 3.2 `src/lib/seo-metadata.ts`

**`og:type` / `og:url` 缺失的真正根因不在 `layout.tsx`。**

`generatePageMetadata()` 里本来就写了 `url` 和 `type: "website"`。问题出在函数末尾把 `...overrides` 摊平：

```ts
// 修复前 —— 调用方只要传了 openGraph（哪怕只为补一张分享图），
// 基础 openGraph 就被整个对象覆盖掉
return {
  openGraph: { url: ..., type: "website", siteName: ..., ... },
  ...overrides,   // ← overrides.openGraph 整体替换，url / type / siteName 一起消失
};
```

首页和 `/engineer` 页正是这种用法（都只传了 `images`）。修复方式是把 `openGraph` 单独解构出来做**深合并**：

```ts
const { openGraph: ogOverride, ...restOverrides } = overrides ?? {};

return {
  openGraph: {
    ...基础字段,
    ...(ogOverride ?? {}),   // ← 只覆盖调用方显式给的键
  },
  ...restOverrides,
};
```

这样两页都修好，且**以后新增页面不会再踩同一个坑**。已加回归测试锁死（§3.4）。

同时把首页 7 个语种的 title、5 个语种的 description 收紧：

| 语种 | title 前 → 后 | description 前 → 后 |
|---|---|---|
| en | 69 → **55** | 168 → **153** |
| ru | 79 → **59** | 171 → **118** |
| es | 72 → **58** | 170 → **139** |
| pt | 71 → **57** | 157（未超，保留） |
| ar | 66 → **55** | 145（未超，保留） |
| fr | 72 → **58** | 162 → **145** |
| hi | 70 → **50** | 162 → **133** |
| zh | 29（未超，保留） | 82 字符 / SITE 分支（未超，保留） |

阈值：title ≤ 60 字符、description ≤ 160 字符。核心关键词（`Used Farm Machinery`、`AgriTrade`、`Export`、`CLAAS`、`John Deere`）一个都没丢。

⚠️ 英文 description 原稿用了两个 `&`，会被 HTML 转义成 `&amp;` 各 +4 字符。修复时把 `& more` 改成 `and more`，彻底消除计数歧义。

### 3.3 `src/app/[locale]/layout.tsx` + 首页 + engineer 页

- `layout.tsx` 的 `generateMetadata` 补 `metadataBase: new URL(SITE_ORIGIN)` 与 `openGraph.type: "website"`（给不走 `generatePageMetadata` 的路由兜底）。
- 首页与 `/engineer` 页的 `BASE_URL` 从 `process.env.NEXT_PUBLIC_APP_URL || "https://usedfarmmach.com"` 改为 `SITE_ORIGIN`。

**为什么要改这个 `BASE_URL`**：`NEXT_PUBLIC_APP_URL` 线上是**裸域**，而全站裸域 308 跳 www，canonical/sitemap/hreflang 输出的是 www。结果同一份页面的 `og:image` 和 JSON-LD 里 `url` 走裸域、canonical 走 www —— **同一份页面声明了两个身份**，白耗抓取预算。改后所有对外 URL 统一到 `siteConfig.domains.canonical`（`.com` 带 www / `.cn` 裸域）。

### 3.4 `src/lib/__tests__/seo-metadata.test.ts`（新增，11 例）

钉三件事：
1. 首页 8 语 title ≤ 60、description ≤ 160，且 8 语一个不缺。
2. **传 `openGraph.images` 后，`url` / `type` / `siteName` 不能丢** —— 直接钉死 §3.2 那个回归。
3. 调用方显式给的 `images` 与 `robots` 仍然生效（深合并不能把 override 吃掉）。

## 5. 上线策略：两段式

| 阶段 | 动作 | 风险 |
|---|---|---|
| 第一步（本 PR） | CSP 以 **`Content-Security-Policy-Report-Only`** 头名上线；4 个安全头用**强制版**一次上齐 | 零。Report-Only 只报告不拦截；4 个安全头本身不改变页面行为 |
| 观察（≥1 天，建议覆盖一个流量高峰） | 按 §4.3② 检查 Console | — |
| 第二步（单独小 PR） | 把 `key` 从 `Content-Security-Policy-Report-Only` 改成 `Content-Security-Policy`，其余一字不动 | 若白名单有漏，对应功能会失效（不是白屏，因为 `'unsafe-inline'` 保住了 RSC payload） |

**为什么 Report-Only 值得单独一步**：扫描器对 Report-Only 不给分（它只认强制头），但换来的是"零成本发现漏项"。CSP 一旦切强制才发现漏了某个域，表现是**静默失效**（图不显示、统计不上报），比报错更难查。

## 6. 本批不做的项

### 6.1 Responsive images（报告未列为失败，但实测是真缺陷）

实测 `.com` 首页：
- 原生 `<img>` 标签 **16 个**
- `srcset` 出现次数 **0**
- `/_next/image` 请求 **0**

⇒ **`next/image` 完全未启用。** 移动端会下载为桌面优化的原图，首屏字节数浪费严重。

**为什么不塞进本批**：这不是"改个配置"能解决的。`next/image` 要求每个 `<img>` 改 `src` → `srcset`、显式给 `sizes`、处理 `fill` vs 固定宽高、确认 `remotePatterns` 覆盖所有图源（现已配 `*.aliyuncs.com` 三个模式，但要逐个核对页面实际图源）。首页 + 列表 + 详情 + 后台，是独立一批活，且**改错的表现是图片全裂**，必须单独验。

**建议**：单独立项，从产品列表页开始（图最多、收益最大），一次一页。老板拍板是否开工。

### 6.2 关键 CSS 内联

见 §1.3-C，收益与风险不成比例，明确不做。

## 7. 附：报告判定与实测不符的三处汇总

复现报告时容易怀疑自己算错，先对这张表：

| 报告说法 | 实测 | 差值原因 |
|---|---|---|
| Meta Description 176 字符 | **168** 字符 | 报告按渲染后 HTML 计数，两个 `&` → `&amp;` 各 +4 |

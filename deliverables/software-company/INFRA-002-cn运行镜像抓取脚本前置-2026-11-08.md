## 1. 现象（实测，非推测）

`docker` 运行镜像（`.cn` ECS 上的 `cn-app`）里直接执行 20 条试跑会失败。三条独立实测证据：

| # | 文件 | 实测内容 |
|---|---|---|
| 1 | `Dockerfile.cn:27` | deps 阶段 `npm ci --only=production && …`；runner 是 Next.js standalone 产物 |
| 2 | `package.json` | `tsx ^4.10.0`、`ali-oss ^6.23.0` **均在 `devDependencies`**；runner 全局只装 `prisma@5.14.0`（`Dockerfile.cn:82`） |
| 3 | `Dockerfile.cn:97–116` | runner 逐个 COPY 了 10+ 个 `.js` 脚本（`import-articles-to-cn.js`、`seed-eu-benchmark.js` …），**没有** COPY `fetch_subsidy_images.ts`；`.github/workflows/deploy-cn.yml` 亦无 `npm i -g` / `docker cp` 兜底 |

⇒ 脚本文件不在镜像内，`tsx` 与 `ali-oss` 也不在镜像内，三个条件同时缺失。

**影响面有限**：`Dockerfile.cn:92` 把 `.next/standalone` 整体 COPY 进 runner，主站 `src/lib/oss-upload.ts` 的 ali-oss 大概率已由 standalone 依赖收集带入，**线上 OSS 上传功能不受威胁**（此项建议在修复时顺带实测确认）。受影响的只有不走 Next 构建的独立 `.ts` 抓取脚本。

---

## 2. 根因归类

1. **运行时依赖错放 devDependencies**：`npm ci --omit=dev` / `--only=production` 会跳过 devDeps。npm 官方定义 `dependencies` = 生产运行时必需，`devDependencies` = 仅本地开发/测试；运行时 `import` 的包放错位置，是典型的「部署后 `Cannot find module`」根因。
2. **生产容器跑未编译 `.ts`**：tsx 是开发/一次性脚本的运行时转译器，官方 CAVEATS 明确 **"For production, pre-compile TypeScript with tsc"**。
3. **新增脚本未进入镜像 COPY 清单**：`scripts/` 下脚本是**逐个显式 COPY** 的模式，新增脚本必须同步加一行。

---

## 3. 官方依据（2026-11-08 web 查证）

| 来源 | 要点 |
|---|---|
| npm 官方文档 `docs.npmjs.com/specifying-dependencies-and-devdependencies-in-a-package-json-file` | `dependencies` = production required；`devDependencies` = local development and testing only；`--omit=dev` 跳过后者 |
| ali-oss npm 包官方安装说明 | `npm install ali-oss --save`（即进 **dependencies**），非 `--save-dev` |
| tsx 官方 man / CAVEATS | "For production, pre-compile TypeScript with tsc"；tsx 不产出 JS、不做类型检查 |
| 多阶段 Docker 通行做法 | builder 全量 `npm ci` + 编译产出 `.js`；runner `npm ci --omit=dev`，只 COPY 编译产物，不带编译器 / `.ts` 源码 / devDeps |

---

## 4. 修复方案（三步，按官方正解）

> 均在**后续独立任务**中实施；实施时同样遵守 additive-only，PR 由用户亲自开/合并。

1. **`ali-oss` 移入 `dependencies`**：从 `devDependencies` 移到 `dependencies`，同步 `package-lock.json`。理由：运行时 `import` 的 SDK 必须进生产依赖。
   - ⚠️ 同时确认 `@/lib/db` / `src/lib/oss-upload.ts` 是否已有其他运行时依赖被误放 devDeps，避免同类问题。
   - ⚠️ **不要**把 `tsx` 一并移入 dependencies（见第 2 步）。
2. **builder 阶段预编译抓取脚本**：在 `Dockerfile.cn` 的 builder（该阶段是 `npm ci` 全量、含 devDeps）用 `tsc` 或 `esbuild` 把 `scripts/fetch_subsidy_images.ts` 产出为单个 `.js`（CJS/ESM 与 runner 的 `type` 一致），处理 `@/` 路径 alias，外部依赖（`ali-oss` / `@prisma/client`）保留为 `require`。
3. **runner 只 COPY 编译后的 `.js`**：仿 `Dockerfile.cn:97–116` 既有写法加一行 `COPY --from=builder … /app/scripts/fetch_subsidy_images.js ./scripts/fetch_subsidy_images.js`；runner 保持 `npm ci --omit=dev`，**不装 tsx**、不带 `.ts` 源码。运行命令从 `npx tsx scripts/fetch_subsidy_images.ts` 改为 `node scripts/fetch_subsidy_images.js`，参数 `--seed-file` / `--limit 20` 不变。

**明确不做**：❌ 不在生产容器 `npm i -g tsx ali-oss`（反模式：运行时转译 + 容器重启即丢 + 需联网拉包）；❌ 不手写 OSS 签名（继续用 `ali-oss` SDK）；❌ 不改 `.cn` 数据流向（仍只在境内 ECS + `oss-cn-beijing`）。
